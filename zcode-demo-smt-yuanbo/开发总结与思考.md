# 开发总结与思考 — 云ERP教程中心（RE00001）

> 作者：yuanbo ｜ 2026-08 ｜ 工具：zcode 插件（Claude Code 内核）全流程流水线


## 一、项目怎么跑下来的（过程回顾）

完整走了 zcode 七段流水线：`/zcode:prd`（草稿→契约冻结→3 轮评审）→ `/zcode:ui`（17 页原型 4 轮 QA）→ `/zcode:architect`（技术方案评审 95 分）→ `/zcode:breakdown-task`（43 任务 3 轮评审 90 分）→ `/zcode:backend`（19 任务）→ `/zcode:frontend`（24 任务）→ `/zcode:gen-test` + `/zcode:run-test`（545 案例 + 33 E2E + 160 单测全绿）。

一个直观的数字：**41/41 任务完成、PRD 3 轮评审从 12 个 P0 修到 0、技术方案 95 分、任务拆分 3 轮从 81 到 90、前端代码审查 90 分、复刻评审必修项闭环修复**。质量不是一次写对的，是评审循环逼出来的。

我个人是前端开发工程师，平时是使用claude code AI编程工具，这次作业花了2-3天，全程是claude code+zcode进行Prd设计+编码+自动化测试等工作。个人感受如下：zcode 设计比较完善复杂，本次需求明确，产出的产物明确，从0到1开发比较适合zcode。这次完善的体验了 zcode 的开发，觉得zcode是一个比较完善健全的开发工具，从prd到产物的质量都不错，但是就是耗时比较长，不适合日常简单开发任务。

## 二、实操遇到的真实问题（按踩坑顺序）

### 1. Windows 中文环境的"乱码幽灵"
**现象**：AI 写入含中文的 md 文件时，随机出现 U+FFFD 乱码字符（写 PRD 术语表"13态订单"变成"13态订��"），且我自己用 Edit 修复时又引入新的乱码——一度陷入"修一处坏一处"。

**解决**：zcode 插件的 PostToolUse hook 每次写入后自动扫描并报出磁盘真实字节，我只需要按报错行做精准 Edit；后来形成了"大段中文写入后必跑一遍 `python -c` 全文 U+FFFD 扫描"的肌肉记忆，全项目最终零乱码。

**思考**：这类"环境特异性"问题（Windows + Git Bash + GBK 控制台 + UTF-8 文件的编码链）恰恰是纯 AI 推理最容易翻车、而人一眼能看出不对的地方。**hook 把机器擅长的事（逐字节扫描）自动化，把人擅长的事（判断哪句话该是什么）留给人机协作**——这是 AI 工具设计的一个好范式。

### 2. "评审-修复"循环里的收益与陷阱
PRD 第一轮评审挖出 12 个 critical，最有价值的一个是：**"已发布教程编辑回审被驳回后，前台该展示什么"**——草稿态按字面语义会让曾发布的教程从三端消失，违反"旧版不断供"契约。这个边界我写 PRD 时完全没意识到，三个专家 Agent 从不同角度（流程归宿/状态机/一致性）撞出了同一处矛盾。

修复后我把它落成了数据库层面的硬保证：`published_content` 快照列 + `last_offline_at` 时间戳 + 单条 `VISIBLE_SQL` 全站共用——评审发现的业务洞见直接变成了技术方案的核心设计（tech-design §4），后续 7 个模块全部 import 这一个常量，杜绝口径漂移。

**陷阱也真实存在**：AC 评审 3 轮分数 75→82→77（不升反降），根因是我第二轮新增的条目引入了新的 GWT 结构问题（Given 里混操作、Then 里含用户行为），被可判定性专家逐条扣分。**评审分数不是单调上升的，"修问题"本身会引入新问题**——好在 3 轮封顶+降级通过的机制兜住了收敛性。

### 3. 并行开发的进程级冲突
多个开发 Agent 并行自测时反复出现诡异失败：固定值断言随机挂、测试全量卡死无输出。排查发现两个根因：
- **僵尸进程持锁**：前序 Agent 的临时 server 没杀干净（Windows 下 Node 25 的 libuv 退出断言问题），3000/3100 端口被占 + erp.db 文件锁——杀掉 PID 后 106 个测试立刻全绿；
- **共享库并发写**：`npm test` 多进程并行跑时争用同一个 erp.db 触发 SQLITE_BUSY，最终把 test 脚本固定为 `--test-concurrency=1` 串行（这个决策被两个独立 Agent 先后发现并互相印证）。

**思考**：AI Agent 并行不是免费的。本次 5 个 Agent 并行开发时，我在派发时强制"不许改 routes/index.ts（挂载归主 Agent 统一）""报告目录带迭代前缀"，仍然漏了报告同名覆盖（BE-01 三个迭代同名，互相覆盖了 4 份报告，靠会话记录补写）。**并行边界要按"文件归属"显式划分，靠约定不靠自觉**。

### 4. 会话中断三次，为什么没丢工作
开发过程中 Claude Code 进程退出过 3 次（批次 3、批次 6、以及一次 Workflow 中断）。每次恢复时：磁盘上的代码都在（Agent 是先落盘再汇报），用 SendMessage 按 agentId 唤醒后它还能带着之前的上下文继续收尾——最惊险的一次是 admin 审核队列 Agent 在"收尾确认"阶段停摆，恢复后只用了几步就确认交付物完整。

**但代价真实存在**：IT-02/FE-06（目录管理）在一次中断中处于"代码落盘了、任务没标记"的状态，恢复时我先 `git status` 核对再补派 Agent"补完而非重写"，它顺手修掉了前任留下的 3 个真实 bug（拖拽相邻移动静默失效最有意思：新旧 sort 恰好相等导致双双漏提交，纯逻辑边界）。

### 5. 两个"评审才发现"的高价值缺陷
- **recommend 不解析 token**：前端联调时发现已登录推荐位恒回全站口径——后端自测全绿（因为自测只测了 query 参数路径），跨端联调才暴露。修复后记入 CHANGE-6 并把"query > token > global"优先级写进契约。
- **h2 步骤标题链路断裂**：代码审查发现 admin 富文本编辑器产出 `<h2>` 步骤标题，但 portal 详情页白名单没有 h2、拆节只认 h3——**运营用编辑器创作的教程发布后目录/步骤/进度会整体消失**。种子数据全是 h3 所以 E2E 终验 33 绿也没暴露。修复用真实 UI 全链路验证（编辑器创作 h2 步骤→提审→过审→portal 详情断言目录 4 项/进度 67%），这类"数据巧合掩盖链路缺陷"的教训很值得记：**测试数据要覆盖生产的另一种真实**。

### 6. Playwright chromium 装不上
官方 CDN 在本机不可达（两轮 0% 卡死），最后用 `PLAYWRIGHT_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright` 镜像装成，还要清理超时残留的 `__dirlock`。内网/受限网络环境跑 AI 工具链，镜像源是第一反应。

在配置 Playwright 的过程中，我也遇到过环境安装方面的问题。最开始并不是 Playwright 本身的代码问题，而是开发环境、Node/npm 依赖以及浏览器运行环境之间存在关联，所以单纯重复执行安装命令并不能解决问题。

我当时的排查思路是先看终端的具体报错，确认到底是 npm 依赖安装失败，还是 Playwright 浏览器本体没有安装完整，然后检查当前 Node.js 和 npm 环境，再重新安装相关依赖。安装完成后，还需要确认 Playwright 所需要的浏览器环境是否准备好，否则 MCP 虽然能够正常启动，但真正执行页面访问、截图或自动化操作时仍然可能失败。

这次问题让我比较直观地认识到，AI Coding 工具并不是安装完成就代表整个能力可用。像 Playwright 这种涉及 Node 依赖、浏览器运行环境和 MCP 的工具，需要按照“依赖安装 → 浏览器环境 → MCP 配置 → 实际调用”的顺序逐层验证。后来我在自己的 Claude Code 工作流中使用 Playwright，重点也从“把工具装上”转变成了“确认工具能够真正参与需求验证”。


## 三、对 AI 如何更好落地的思考

### 1. 流水线的价值在"门禁"而不在"生成"
zcode 这套流水线最值钱的不是 AI 写代码快（那只是省力），而是每一段都有**可失败的门禁**：PRD 契约评审 P0 清零才能过、任务拆分 90 分才能过、复刻评审必修项修完才能过代码审查、测试全绿才能出验收报告。AI 生成的质量方差大，**门禁把方差的下限兜住了**。反过来说：如果没有这些门禁，同样的 AI 一次性生成 40 个文件，我根本不敢直接用。

### 2. "人工卡口"要少而准
整条流水线只有 5 个人工介入点：PRD 草稿评审、契约冻结、技术决策 4 问、文档对齐 2 次、测试报告评审。每个都值得停——它们是**方向性决策**（错了返工整个下游）。而"覆盖率 15% 怎么办""评审 3 轮不过怎么办"这类执行性决策全部自动降级+诚实记录。**把人的注意力当稀缺资源设计**，是 AI 工作流能不能被真实用的关键。

### 3. AI 的产出必须"可追溯"，否则不敢信
本次所有关键决策都有落点：业务洞见→PRD 可见性规则→VISIBLE_SQL 常量→7 处 import，一条线能从验收标准追到代码；所有偏离→change-log（CHANGE-1~10，每条含变更前/后/原因/关联任务）→人工审核→合并基线。**AI 改了什么、为什么改，机器自己记账，人只审账**。没有这个机制，AI 越能干人越害怕。

### 4. 诚实的降级比虚假的通过有价值
gen-test 覆盖率 15% 是编号约定错配（545 条案例真实存在、结构 89 分），我在 case-gen-report 里原样记录了"为什么低、实际资产是什么、怎么修"，而不是把数字粉饰过去。**交付物里最有说服力的恰恰是这些如实记录的褶皱**——它证明流程真的跑过、问题真的遇到过。

### 5. 仍然必须由人做的事
- 判断"哪个 P0 先修、哪个 warn 可以放过"（评审报告只给清单，取舍是人的）
- 环境特异性问题（编码/网络/进程锁——AI 的默认假设常不对）
- 真实业务语感（"新手入门"vs 原型"新手上路"哪个对——PRD 术语表是准绳，但建立准绳的是人）
- 最后看一眼截图（复刻评审的 AI 读图会误报，admin 端"提审按钮"其实是"提交审核"，人工复核才澄清）

开发人员加上ai编程的过程中，开发人员从原来的注重编码变成了更加注重判断，判断ai怎么做，产出什么，产出的对不对。对于我自己来说，ai已经全面参与进了我的工作中，我更多像一个管理者，管理和指挥ai进行工作，我做一些保证交付质量的工作和负责。

结合我目前的前端开发工作，我认为 AI 最适合参与的并不是简单替代开发人员写代码，而是把研发过程中大量重复、机械和需要反复切换上下文的工作自动化。

目前我已经开始尝试把 Claude Code、OpenSpec、MCP、Playwright 等工具组合起来。例如，需求进入开发阶段后，可以先通过 SDD 明确需求、技术方案和任务，再让 AI 根据任务进行代码实现；遇到 Issue 时，可以结合 ONES、GitLab 等 MCP 获取上下文，辅助完成问题定位和修复；涉及页面效果时，再通过 Playwright 进行实际页面验证。这样 AI 就不再只是一个“代码生成器”，而是逐渐成为研发流程中的一个 Agent。

从我的岗位来看，未来更值得投入的是建立一套稳定的 AI Coding 工作流，而不是单独学习更多 AI 工具。开发人员仍然需要负责需求理解、架构设计、技术决策和最终验收，AI 则负责信息检索、代码实现、测试验证、问题排查以及一些标准化操作。这样可以把人的精力更多放在复杂问题和技术决策上，同时减少重复性的开发工作。

我目前已经在自己的 Claude Code 环境中尝试通过 Command、Agent、Hook 和 MCP 组织这些能力。下一步我更希望把这套个人工作流进一步沉淀成团队可以复用的研发规范，让 AI Coding 从“个人使用技巧”逐渐变成“团队研发能力”。


## 四、个人感受

这次学习给我最大的感受是，我以前对 AI Coding 的理解还是偏向“让 AI 帮我写代码”。真正开始使用 Claude Code、OpenSpec 和 MCP 后，我发现写代码反而不是最难的问题。对于简单需求，AI 的代码生成速度已经很快；真正影响最终结果的是 AI 有没有正确理解需求、有没有获取到足够的项目上下文，以及有没有一个明确的验证标准。

尤其是在复杂需求中，如果直接把需求丢给 AI，很容易出现理解偏差，甚至为了完成一个小需求修改大量无关代码。SDD 给我的启发比较大，它实际上是在 AI Coding 前面增加了一层约束，把需求、方案、任务和验收标准先明确下来，再让 AI 去执行。这样虽然前期多了一些工作，但能够减少后面反复修改的成本。

所以我现在更倾向于把 AI 看成一个执行能力很强的开发助手，而不是完全替代开发人员。开发人员真正需要提升的能力，会逐渐从“怎么写代码”转向“怎么描述问题、怎么设计流程、怎么约束 AI，以及怎么验证 AI 的结果”。这也是我这次学习之后对 AI Coding 最大的认识变化。
